For camera makers

The MCVSAID timing strip, version 1

A frame timestamp drawn into the picture, so that the exact capture time of every frame reaches the production software through any route the video takes.

MCVSAID (the MultiCam Video Stream AI Director) cuts between many cameras live. It needs to know when each frame it shows was captured. The camera draws its clock into a thin black-and-white strip along the top edge of every frame, and MCVSAID reads the strip back from the finished picture. This works over SRT, RTSP, NDI®, RTMP or a capture card. This page is the whole specification, with an example video and a reference reader to test against.

Version and licence

This is version 1 of the format, and version 1 will not change. Anything added later will be a new version that readers can tell apart from this one, and readers will keep reading version 1.

Example and reference reader

  • example-1080p30.mp4: the video above. The same stream as MPEG-TS, as SRT carries it: ffmpeg -i example-1080p30.mp4 -c copy -f mpegts example-1080p30.ts.
  • read_strip.py: the reference reader (Python 3 and the ffmpeg command line). It decodes every frame of a file or a live stream and prints the time in each.

Why it is needed

A production system must line every camera's picture up with every other camera and with the sound. Each camera's picture arrives late by a different amount, and that amount changes: encoder, network, decoder and mixer buffers all add to it. With the capture time inside the picture, the system can measure each camera's real delay at the point where the picture is shown, and correct it automatically. A timestamp in the stream's metadata alone does not get that far, because OBS and most mixers drop it. Pixels get through everything.

MCVSAID's own phone cameras already do this. We are asking network cameras to do the same.

The value

  • The UTC wall-clock time in milliseconds since 1970-01-01 (Unix time × 1000) of the moment the frame was captured, keeping only the low 32 bits: value = ms & 0xFFFFFFFF. The reader restores the full time from its own clock. The low 32 bits repeat only every 49.7 days.
  • "Captured" means as close to the sensor as you can manage: the start or the middle of exposure is ideal. What matters most is that the gap between that moment and the time written is the same for every frame, at every resolution and frame rate. Please say in your documentation which moment you use.
  • One new value per frame, never repeated: at 30 fps the values step 33 or 34 ms, at 60 fps 16 or 17 ms.

The clock

  • Keep the clock on NTP, with a server the user can set and an update interval that can be as short as 1 minute.
  • Please slew the clock (adjust its rate) rather than step it, so that consecutive frames never jump.
  • On a wired network with a local NTP server, the clock should stay within ±2 ms of the server.

The layout

The strip is drawn over the top rows of the picture, across its full width.

  • Height: round(picture height × 16 / 1080) pixels: 11 at 720p, 16 at 1080p, 21 at 1440p, 32 at 2160p.
  • 44 equal cells from left to right. Cell i covers columns floor(i × W / 44) to floor((i + 1) × W / 44) − 1, so cells are 43 or 44 pixels wide at 1920.
  • Each cell is solid white (Y = 235 in limited range, 255 in full range) or solid black (Y = 16, or 0 in full range), with neutral colour (Cb = Cr = 128).
CellsContent
0white (start marker)
1black (start marker)
2 to 33the 32-bit value, most significant bit first; 1 is white, 0 is black
34 to 41the 8-bit check byte, most significant bit first
42 and 43white, white (end marker)

The two ends differ on purpose, so a mirrored picture can still be read. Readers also look at the bottom edge, so a picture turned upside down is read too.

The check byte

The four bytes of the 32-bit value XORed together, then XORed with 0x5A:

uint8_t check = (uint8_t)((v >> 24) ^ (v >> 16) ^ (v >> 8) ^ v ^ 0x5A);

Worked example, the first frame of the example video:

time          2026-01-01 12:00:00.000 UTC = 1767268800000 ms
low 32 bits   1767268800000 & 0xFFFFFFFF = 2037241344 = 0x796DD600
check         0x79 ^ 0x6D ^ 0xD6 ^ 0x00 ^ 0x5A = 0x98
cells 0-1     1 0
cells 2-33    01111001 01101101 11010110 00000000
cells 34-41   10011000
cells 42-43   1 1

Where in the camera

  • Draw it after all picture processing (white balance, exposure, LUTs, scaling, text overlays) and just before the encoder, so that the strip stays exactly black and white.
  • Put it on every output the camera has: SRT, RTSP, NDI, RTMP, and HDMI or SDI where practical. All outputs carry the same value for the same frame.
  • Nothing should scale, blur or sharpen it after it is drawn, other than the encoder itself. Readers tolerate normal compression: the reference reader averages the middle of each cell and splits black from white halfway between the darkest and the lightest cell. The example reads on every frame at 4 Mbit/s.

Turning it on and off

  • An on/off setting, off by default, kept across restarts.
  • Settable from the camera's HTTP API and its web page, for example as timing_strip_en=0|1 in the request that sets other picture or overlay options, and readable back from the matching settings read.
  • It takes effect from the next frame, with no restart of the stream.

Testing an implementation

  1. Point the reference reader at the camera's stream, or at a recording of it. With --live it also prints each frame's age by the test computer's clock. (192.0.2.10 stands for the camera's address; an srt:// address needs an ffmpeg built with libsrt.)
  2. Every frame reads, at every resolution and frame rate the camera offers, at its lowest bitrate.
  3. The step between frames is the frame interval, ±1 ms, with no repeats and no jumps, including across an NTP update.
  4. With the camera and the test computer on the same NTP server, the age stays steady over 10 minutes. It is the camera's real delay plus the decoder's.
  5. Every output (SRT, RTSP, NDI and so on) shows the same value for the same frame.
python3 read_strip.py --live "srt://192.0.2.10:9000?mode=caller"

A recording of these five steps is all we need to support your camera in MCVSAID.

Optional: the same time in the stream's metadata

MCVSAID does not read this today. If your encoder can also put the full 64-bit millisecond value into each frame's H.264 or H.265 SEI (user_data_unregistered), tools that read metadata can use it too. The strip in the picture is still the part that is needed, because it is the only one that survives a production mixer.
